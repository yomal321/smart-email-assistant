# Spec: Dashboard Actions & Drafts API (Backend Phase 2 of 6)

**Change:** 010-dashboard-actions-drafts-api
**Created:** 2026-09-14
**Status:** 🟡 Draft

## Overview

Phase 2 does for Action items and Drafts what `009-dashboard-messages-api` did for the inbox: enrich the schema, fix/extend the one n8n workflow node that would otherwise break or under-serve it, build the API tier, and rewire the provider that gates whether the page shows real data.

Two independent verticals land in the same change because they share a precedent, not because either depends on the other's table:

1. **Tasks** — migration `0009_tasks_enrichment.sql` drops `tasks_email_id_key` (currently caps extraction at one task per email) and adds `owner_name`/`owner_email`/`priority`/`origin`/`confidence`. `n8n/workflows/action-extraction.json`'s `Write task` node must change regardless of anything else in this spec: its `INSERT ... ON CONFLICT (email_id) DO NOTHING` targets a constraint this migration removes, and a `PostgreSQL` `ON CONFLICT` clause naming a column with no matching unique constraint is a runtime error on every subsequent extraction, not a silent no-op.
2. **Drafts** — migration `0008_drafts_enrichment.sql` adds `generated_body`/`tone`/`length`/`approved_at`/`edit_distance`. `n8n/workflows/draft-generation.json`'s webhook currently accepts only `{email_id}` and has no notion of tone or length at all — this is a real content change (accept the two new fields, use them in the prompt, persist `generated_body`), not a query fix.

A third piece of scope was discovered by reading the actual frontend rather than trusting the proposal's route list (the same discipline `009`'s design doc applied): `app/drafts/page.tsx` calls `getMessageById(draft.messageId)` from the **fixture** `lib/data` module and does `if (!message) return null` per draft — a fixture lookup against a real Supabase-backed `draft.messageId` will essentially always miss, meaning every pending draft would silently disappear from the page once `drafts-provider.tsx` is wired to live data, with no error and no visible symptom beyond an empty list. `009`'s design.md deliberately dropped `GET /api/messages/:id` for having zero caller at the time; this phase gives it a real one, so it is back in scope — see Notes for why this isn't scope creep.

## Requirements

### Functional Requirements

**Tasks / Action items**

- **FR1.** Migration `0009_tasks_enrichment.sql`: drop the `tasks_email_id_key` unique constraint on `tasks.email_id`; add `owner_name text`, `owner_email text`, `priority text not null default 'normal' check (priority in ('urgent','normal','low'))`, `origin text not null default 'extracted' check (origin in ('extracted','manual'))`, `confidence int`; drop and recreate `tasks_status_check` to `check (status in ('todo','in-progress','done','dismissed'))`. `owner_name`/`owner_email`/`confidence` stay nullable — nothing in this phase populates them beyond what FR2 sets.
- **FR2.** `n8n/workflows/action-extraction.json`'s `Write task` node: remove `ON CONFLICT (email_id) DO NOTHING` (every extraction now inserts unconditionally — there is no longer a constraint to conflict against), and add explicit `priority = 'normal'`, `origin = 'extracted'` to the `INSERT`'s column/value list (matching the column defaults, written explicitly per the workflow's existing convention of never relying on a column default — see `Write triage success`/`Write draft` for precedent). The extraction prompt, schema, and validator (`Build extraction prompt`, `Validate extraction result`) are **not** touched — still one `has_task`/`task_text`/`deadline` decision per call.
- **FR3.** `GET /api/action-items?status=` — reads `tasks` joined enough to build the dashboard's `ActionItem` shape (`text`, `sourceMessageId` = `email_id`, `owner`, `dueDate` = `deadline`, `priority`, `status` mapped `open→todo`/unchanged otherwise per Edge Cases, `origin`, `confidence`). `status` is optional; omitted means all tasks.
- **FR4.** `POST /api/action-items` `{text: string, dueDate: string | null}` — the manual-add path only (mirrors `action-items-provider.tsx`'s current `addManual`). Inserts a `tasks` row with `email_id = null`... **correction, see Notes**: `tasks.email_id` is `not null` (FR1 does not relax that) — manual items need a resolution; see Notes for the decision this FR implements. Writes `origin = 'manual'`, `confidence = null`, `status = 'todo'`, `priority = 'normal'` (matching the provider's current default), `owner_name = null`/`owner_email = null` (renders as `"you"` per FR3's mapping).
- **FR5.** `PATCH /api/action-items/:id` `{status?, dueDate?, priority?}` — partial update, at least one field required; only supplied fields change. Backs both the Kanban drag (status only) and the list view's checkbox (status only).
- **FR6.** `GET /api/action-items/export.csv` — same rows as FR3 (optionally filtered by the same `status` param), rendered as `text/csv` with a header row (`text,dueDate,priority,status,owner`) — the live-data equivalent of whatever the Export → CSV button currently produces from fixtures.

**Drafts**

- **FR7.** Migration `0008_drafts_enrichment.sql`: add `generated_body text`, `tone text check (tone in ('formal','friendly','brief','firm'))`, `length text check (length in ('brief','standard','detailed'))`, `approved_at timestamptz`, `edit_distance int`; drop and recreate `drafts_status_check` to `check (status in ('pending','approved','sent','discarded'))`.
- **FR8.** `n8n/workflows/draft-generation.json`: the `Verify secret` node (or a node immediately after it) reads `tone` and `length` off the webhook's JSON body alongside the existing `email_id`, defaulting to `'friendly'`/`'standard'` when either is absent or not one of the allowed values (never rejecting the request for a bad/missing tone or length — this endpoint's existing failure modes are all auth/existence/cap related, not input-shape related, and FR9's prompt injection stays additive). `Build draft prompt`'s `system_prompt` incorporates both (e.g. appending "Draft in a {tone} tone. Aim for a {length} reply.") without touching the existing style-sample instruction or the prompt-injection defense wording.
- **FR9.** `Write draft`'s `INSERT` gains `generated_body` (set to the same value as `draft_body` — the LLM's raw output, before any edit), `tone`, `length` in its column/value list, and its `RETURNING` clause includes them so `Respond 200`'s echoed row carries the new fields.
- **FR10.** `GET /api/drafts?status=` — reads `drafts` mapped to the dashboard's `Draft` shape (`messageId` = `email_id`, `body` = `draft_body`, `generatedBody` = `generated_body`, `tone`, `length`, `status`, `generatedAt` = `created_at`, `approvedAt` = `approved_at`, `editDistance` = `edit_distance`). `status` optional; omitted means all.
- **FR11.** `POST /api/drafts` `{messageId: string, tone: Draft["tone"], length: Draft["length"]}` — this route does **not** insert into `drafts` itself. It calls the existing `n8n` `POST /webhook/generate-draft` endpoint server-side (`{email_id: messageId, tone, length}` in the body, `x-draft-webhook-secret` header read from a new server-only env var), and relays that call's outcome: n8n's `200` (the inserted row) → `200` with the mapped `Draft`; n8n's `404`/`429`/`502` → the same status code and error body, passed through; a network failure reaching n8n → `502` with a generic error. The browser never sees the webhook secret or talks to n8n directly (same service-role/session-cookie boundary `008` established for Supabase).
- **FR12.** `PATCH /api/drafts/:id` `{body?, tone?, length?}` — partial update. When `body` is supplied, the route computes `edit_distance` (word-level Levenshtein or a simpler word-difference count — see Notes for which) between the incoming `body` and the row's stored `generated_body`, and writes both `draft_body = body` and `edit_distance` together, so `edit_distance` always reflects total drift from the original AI output, not drift since the previous edit.
- **FR13.** `POST /api/drafts/:id/status` `{status: "approved" | "sent" | "discarded"}` — updates `status`; when the new status is `"approved"`, also stamps `approved_at = now()` (only if not already set — approving twice doesn't move the timestamp).
- **FR14.** `GET /api/messages/:id` — a single-row equivalent of `009`'s `GET /api/messages`, reusing `mapEmailRowToMessage` unchanged. Reintroduced this phase because `app/drafts/page.tsx` and `CommitView` require a real message to render a draft at all (Overview, Notes) — not new frontend-facing scope invented here, but a route `009` correctly deferred and this phase correctly un-defers, with the evidence cited.
- **FR15.** `drafts-provider.tsx` and `app/drafts/page.tsx` switch off `getMessageById()`/`getDrafts()` fixtures: fetch-on-mount from `GET /api/drafts` (replacing the `useState(() => getDrafts())` seed), and `app/drafts/page.tsx`'s three `getMessageById(...)` call sites fetch from FR14 instead (a small `useMessage(id)` hook following `use-sync-state.ts`'s template, or inline `useEffect` calls per row — design.md decides which). `updateBody`/`setTone`/`setLength`/`setStatus` become optimistic-update-plus-API against FR12/FR13, following `board-provider.tsx`'s fire-and-forget mutation pattern. Regenerate (currently a 900ms `setTimeout` stub) calls FR11.
- **FR16.** `action-items-provider.tsx` switches off the `getActionItems()` fixture: fetch-on-mount from FR3, `addManual`/`setStatus` become optimistic-update-plus-API against FR4/FR5. `app/actions/page.tsx`'s one `getMessageById(item.sourceMessageId)` call (a subject-line label only, already null-guarded) is **not** rewired this phase — see Notes for why this is a smaller, acceptable, explicitly-documented gap, unlike FR14/FR15's fix for the Drafts page.

**Shared**

- **FR17.** `architect/04-data-model.md` updated to reflect the enriched `tasks` and `drafts` tables, per the convention `006-draft-generation`/`009` established.

### Non-Functional Requirements

- **NFR1.** Every new/changed route selects an explicit column list — never `select("*")`, and never `raw_payload` — matching the field-minimization convention `009`'s routes and `message-mapping.ts` established.
- **NFR2.** No changes to `middleware.ts` or `lib/auth/session.ts` — every new route lives under `/api/**` and is covered by the existing deny-by-default session check as-is.
- **NFR3.** The n8n workflow edits reuse the existing `Supabase Postgres` credential (same name, same placeholder id convention) — no new credential is created, matching every prior phase's write nodes.
- **NFR4.** FR11's webhook secret is a **new, dashboard-side** env var (`DRAFT_WEBHOOK_SECRET`, same name and value as the n8n environment variable of the same name `draft-generation.json`'s `Verify secret` node already reads) plus a webhook URL (`N8N_DRAFT_WEBHOOK_URL`) — both server-only, read only inside the `POST /api/drafts` route handler, added to `.env.local.example` with the same documentation convention that file already uses for `SUPABASE_SERVICE_ROLE_KEY`/`SESSION_SECRET`.
- **NFR5.** Migration `0009` (constraint drop) and the `action-extraction.json` fix (FR2) must ship together — the migration alone breaks every subsequent extraction write, and the workflow fix alone is a no-op without the constraint gone. Call this out explicitly in the migration's own SQL comment (matching `0003`'s/`0004`'s existing header-comment convention), not only in this spec.

## Acceptance Criteria

- **AC1.** After migration `0009`, `insert into tasks (email_id, task_text, status) values ('<existing email id>', 'second task', 'open')` against an `email_id` that already has a task succeeds (FR1) — this was a constraint violation before the migration.
- **AC2.** A live (or pinned-fixture) run of Action Extraction against an email that already has an existing `tasks` row produces a **second** `tasks` row with `priority = 'normal'`, `origin = 'extracted'` (FR2), and does not error.
- **AC3.** `GET /api/action-items` returns every `tasks` row mapped to the `ActionItem` shape, including rows with `origin = 'manual'` and `origin = 'extracted'` side by side for the same `email_id`.
- **AC4.** `POST /api/action-items {text: "call the vendor", dueDate: null}` creates a task visible in a subsequent `GET /api/action-items` with `origin: "manual"`, `confidence: null`.
- **AC5.** `PATCH /api/action-items/:id {status: "in-progress"}` changes only `status`; a second `PATCH` with `{priority: "urgent"}` on the same id leaves `status` at `"in-progress"`.
- **AC6.** `GET /api/action-items/export.csv` returns a `text/csv` response whose row count matches `GET /api/action-items`'s array length.
- **AC7.** After migration `0008`, a `drafts` row can hold `tone = 'firm'`, `length = 'detailed'`, and a `generated_body` distinct from `draft_body` (AC confirms the two columns are independently writable).
- **AC8.** A live (or pinned-fixture) call to the `generate-draft` webhook with `{email_id, tone: "formal", length: "brief"}` produces a `drafts` row where `tone = 'formal'`, `length = 'brief'`, `generated_body` is non-empty, and the LLM's `system_prompt` (visible in the pinned call) contains both the tone and length instructions (FR8/FR9).
- **AC9.** `POST /api/drafts {messageId, tone, length}` against a `messageId` that doesn't exist returns the same `404` shape n8n's webhook already returns, unmodified.
- **AC10.** `PATCH /api/drafts/:id {body: "<edited text>"}` sets `edit_distance` to a value computed against `generated_body`, not against the previous `draft_body` — verified by editing the same draft twice and confirming the second `edit_distance` reflects total drift from `generated_body`, not incremental drift from the first edit.
- **AC11.** `POST /api/drafts/:id/status {status: "approved"}` sets `approved_at`; a second call with the same status does not change `approved_at`'s value.
- **AC12.** `GET /api/messages/:id` for a real `id` returns the same shape `GET /api/messages` would for that row (same `mapEmailRowToMessage` output).
- **AC13.** With `drafts-provider.tsx` and `app/drafts/page.tsx` wired to live data, a `drafts` row with `status = 'pending'` and a valid `email_id` renders on `/drafts` (not silently dropped) — the regression this phase exists to prevent.
- **AC14.** `app/inbox/page.tsx`, `app/review/page.tsx`, `board-provider.tsx`, any Board Sheet component, and `n8n/workflows/triage-pipeline.json`/`email-normaliser.json`/`gmail-ingestion.json`/`gmail-renewal-recovery.json`/`llm-gateway.json` are untouched by this change — verify confirms this with a diff, not just a claim.

## Edge Cases

- **A `tasks` row's `status` was `'open'`/`'done'`/`'dismissed'` under the old check (migration `0003`); FR1 widens the vocabulary but does not rewrite existing values.** `'open'` is not a valid Kanban column (`todo`/`in-progress`/`done`) — FR3's mapping treats `status = 'open'` the same as `'todo'` for every pre-existing row, since `'open'` was `0003`'s starting state and `'todo'` is `0009`'s equivalent starting state. New rows never get `'open'` again (FR2 doesn't write it).
- **A manually-added action item has no source email.** `tasks.email_id` stays `not null` (FR1 doesn't touch that constraint — only the uniqueness). FR4's Notes below record the resolution.
- **`PATCH /api/drafts/:id` with no fields, or `{}`.** Returns `400` — same "at least one field required" contract `009`'s single-field PATCH routes didn't need to state (they always had exactly one field) but this route's multi-field partial update does.
- **`POST /api/drafts` while n8n's regeneration cap (5/hour) is already hit.** The `429` response passes through unchanged (FR11) — this phase does not duplicate or pre-check the cap in the dashboard's own API layer.
- **A pre-`0008` `drafts` row has `generated_body = null`.** `PATCH /api/drafts/:id`'s edit-distance computation (FR12) against a `null` baseline: treat as an empty string (`edit_distance` becomes the full length/word-count of the new `body`) rather than throwing — an honest, if inflated, number instead of a 500.

## Notes

- **Why `GET /api/messages/:id` (FR14) is not scope creep.** `009`'s design.md dropped it with "zero caller for each in the current frontend," and committed to re-adding routes only when a real caller appears rather than pre-building them. Reading `app/drafts/page.tsx` directly (not trusting the proposal's endpoint list) surfaced exactly that: `getMessageById()` gates whether a pending draft renders at all. This phase honors `009`'s own stated policy by adding the route back, with the specific evidence that changed the calculus.
- **`app/actions/page.tsx`'s `getMessageById()` call is deliberately left on fixtures (FR16).** It only supplies a subject-line label next to an action item, already guarded by `item.sourceMessageId ? getMessageById(...) : undefined` with a further `{source && ...}` render guard — worst case, the label silently doesn't show, which is materially different from `app/drafts/page.tsx`'s `if (!message) return null` making the entire item vanish. Rewiring it would mean either building a second variant of FR14's fetch or accepting an extra round-trip per row for a cosmetic label; deferred, and named here so it isn't discovered only by reading a diff.
- **Manual action items and the `email_id not null` constraint (FR4).** Two ways to resolve this were considered: (a) relax `tasks.email_id` to nullable in migration `0009` alongside dropping the uniqueness constraint, or (b) keep `email_id not null` and have manual adds require picking a source message client-side (a larger UI change `action-items-provider.tsx`'s current `addManual(text, dueDate)` signature doesn't support — it takes no message reference at all). **Decision: (a)** — relax `tasks.email_id` to nullable as part of migration `0009`'s column changes (not just drop the uniqueness constraint), since `0003`'s own comment already frames the `not null` FK as specifically a hallucination-mitigation device for *extracted* tasks ("every task is always checkable against its source email") — a rationale that doesn't apply to a manually-typed item with no extraction behind it. FR1's migration description is amended to include `alter column email_id drop not null`. `origin = 'manual'` rows are the only ones ever written with `email_id = null`; FR2's extraction write path is unaffected (it always has a real `email_id`).
- **`edit_distance` units (FR12).** Recommend a word-level count (split both strings on whitespace, count differing positions plus a length-difference term — not a full character-level Levenshtein, which is overkill for what the approval-history table displays as "N words" per `app/drafts/page.tsx`'s existing `{d.editDistance ?? 0} words` label). Design.md picks the exact algorithm; this spec fixes only the unit (words, not characters) so the existing UI label stays accurate.
- **Backfill.** Existing `tasks` rows get `priority = 'normal'`/`origin = 'extracted'` from column defaults (FR1); existing `drafts` rows get `null` `tone`/`length`/`generated_body` (FR7). Accepted per `009`'s own precedent for `emails.status` defaulting to `'open'` for pre-existing rows — called out here as a known, accepted gap (a pre-`0008` draft's approval-history row shows no edit-distance-against-original) rather than silently absorbed.
