# Spec: Dashboard Messages API (Backend Phase 1 of 6)

**Change:** 009-dashboard-messages-api
**Created:** 2026-09-14
**Status:** 🟡 Draft

## Overview

Closes `BACKEND-REQUIREMENTS.md`'s "single biggest gap": Triage Pipeline writes `category` + `summary`, but the dashboard's Inbox, Board Sheet, Review queue, and Overview render `priority`, `confidence`, `reasons[]`, `tone`, `tldr`, `entities`, `status`, and a 7-value `platform` — none of it backed by a column. This change enriches the schema, enriches what Triage writes into it, and exposes it through `008-dashboard-api-foundation`'s API tier.

**Investigation changed the route list this spec ships, from what `proposal.md` sketched.** Reading the actual consumer files (`app/inbox/page.tsx`, `app/review/page.tsx`, `app/page.tsx`, `components/board/board-list.tsx`) shows every one of them derives its view — including the review-queue split, platform counts, KPIs, and the priority queue — by filtering/sorting the single in-memory array `board-provider.tsx` holds. None of them fetch a message by id (`board-list.tsx` opens the sheet with `messages.find(m => m.id === openId)` over the array already in memory) or call a dedicated counts/review-queue/overview endpoint. Building `GET /api/messages/:id`, `GET /api/messages/counts`, `GET /api/review-queue`, and `GET /api/overview` as separate routes would mean either shipping code with zero caller, or rewriting these pages to call them instead of the client-side derivation they already do correctly — more frontend churn than the fixture-parity goal calls for. This spec builds the smaller, fully-consumed route set instead: one bounded list read, the mutations, and one real analytics read for the one genuinely separate fixture call site (`getVolumeTrend()`). See Notes for the full reasoning.

## Requirements

### Functional Requirements

**Schema (migration `0005_dashboard_message_enrichment.sql`)**

- **FR1 — New columns on `emails`, `platform` distinct from `category`.** Adds `platform` (text, own `emails_platform_check` constraint: `needs-reply`, `meeting`, `invoice`, `fyi`, `newsletter`, `automated`, `spam-ish`), `confidence` (int), `priority` (text, check `urgent`/`normal`/`low`), `priority_score` (int), `reasons` (jsonb), `tone` (text, check `tense`/`neutral`/`warm`), `tone_evidence` (text), `tldr` (text), `entities` (jsonb), `attachments` (jsonb), `gmail_url` (text), `is_unread` (boolean, default `true`), `is_starred` (boolean, default `false`), `status` (text, default `'open'`, check `open`/`archived`/`snoozed`/`done`), `snoozed_until` (timestamptz), `handled_at` (timestamptz), `handled_action` (text, check `archived`/`done`/`snoozed`), `sla_target_hours` (int, nullable, no default), `model_run` (text), `processed_at` (timestamptz), `is_from_user` (boolean, default `false`). **`category` and its existing `emails_category_check` (5-value) constraint are untouched** — see Notes for why this departs from `proposal.md`'s literal wording.
- **FR2 — `attachments`, `sla_target_hours`, and `is_from_user` are honest placeholders in this phase.** The column exists so later phases don't need another migration to add it, but nothing in this change's scope writes a non-default value: `attachments` stays `null` (Triage isn't asked to produce it — that's Gmail MIME data, not something an LLM infers from subject/body), `sla_target_hours` stays `null` (per `proposal.md`'s resolved open question), `is_from_user` stays `false` for every row this phase touches (sent-mail ingestion is Phase 3).

**Triage Pipeline (`n8n/workflows/triage-pipeline.json` edit, not a new workflow)**

- **FR3 — Same inputs, richer prompt.** "Build triage prompt" keeps its existing `email_id`/`subject`/`body` inputs and the existing 2000-character body truncation (FR10 of `004-triage`, unchanged) — entity/tone/priority extraction is scoped to what's inferable from subject + body, same as category/summary always were. `system_prompt` and `response_schema` are extended to also request: `platform` (7-value enum), `confidence` (0–100), `priority` (`urgent`/`normal`/`low`), `priority_score` (0–100), `reasons` (array of short strings), `tone` (`tense`/`neutral`/`warm`), `tone_evidence` (string or null), `tldr` (string or null — long threads only, so the model may return null), `entities` (object: `dates`, `amounts`, `people`, `links`, `addresses`, each an array, empty array not null when none found). `category` and `summary` stay in the schema exactly as `004-triage` left them.
- **FR4 — Validator extended, same defense-in-depth posture.** "Validate triage result" keeps its existing category/summary checks (FR5/FR9 of `004-triage`, unchanged) and adds equivalent shape checks for every new field: `platform` in the 7-value list, `confidence`/`priority_score` are integers in `[0,100]`, `priority` in the 3-value list, `tone` in the 3-value list, `reasons` is an array of strings (empty allowed), `entities.*` are arrays (missing sub-key defaults to `[]`, not a validation failure — the model may reasonably omit an empty category). Any single field failing validation fails the whole result (routes to the existing failure-write branch, `triage_error` set) — this is one LLM call producing one coherent record, not independently-gradeable fields.
- **FR5 — Write success extends the same guarded UPDATE.** "Write triage success" keeps its `WHERE category IS NULL` idempotency guard (unchanged — `category` is still written first-and-only-once by this workflow, so it remains a valid one-time guard) and extends the `SET` list to write all of FR1's new columns from the validated result, plus `processed_at = now()` and `model_run = 'gemini-3.6-flash'` (the model id `llm-gateway.json`'s HTTP node currently calls — read from that file, not invented).

**API (`gmail-dashboard/app/api/**`, built on `008-dashboard-api-foundation`'s server client + auth guard)**

- **FR6 — `GET /api/messages`, bounded, maps to the full `Message` shape.** `select * from emails order by received_at desc limit 500` (see Notes for the bound). Each row maps to the dashboard's `Message` interface (`lib/data/types.ts`): `sender`/`recipients` are synthesized minimal `Contact` objects from the `participants` jsonb (`id`: the email address, `name`/`email` from the participant, `domain` parsed from the address, `avatarUrl: null`, `isVip: false`, `messageCount: 0`, `yourAvgReplyHours: null`, `lastContactAt`: that email's `received_at`, `openThreadIds: []`, `toneHistory: []` — real values need the `contacts` table, Phase 3); `thread: []` (needs `thread_entries`, Phase 3); `ai.actionItemIds`: `select id from tasks where email_id = $1` (0 or 1 result — `tasks.email_id` is still `UNIQUE` until Phase 2's migration `0009`); `ai` itself is `null` when `platform is null` (not yet triaged or `triage_error` set), matching the existing `needsReview()` convention exactly; `sla.targetHours`: `0` when `sla_target_hours is null` (FR2), `sla.state`: always `"ontime"` in that case, `sla.overdueBy: null` — never a fabricated overdue figure.
- **FR7 — Query parameters accepted but unused by this phase's frontend.** `status`, `platform` (repeatable), `unanswered` filter params from `BACKEND-REQUIREMENTS.md` §5.3 are implemented server-side (useful for direct/future API consumers and match the documented contract) but `board-provider.tsx` calls the route with no parameters, matching the fixture's `getMessages()` (returns everything) — filtering/sorting stays client-side exactly as it is today (see Notes).
- **FR8 — Six mutation routes, mirroring `board-provider.tsx`'s reducer exactly.** `POST /api/messages/archive` `{ids[]}` → `status='archived', handled_at=now(), handled_action='archived'`. `POST /api/messages/done` `{ids[]}` → `status='done', handled_at=now(), handled_action='done'`. `POST /api/messages/snooze` `{ids[], until}` → `status='snoozed', snoozed_until=$until, handled_at=now(), handled_action='snoozed'`. `POST /api/messages/restore` `{ids[]}` → `status='open', handled_at=null, handled_action=null, snoozed_until=null`. `PATCH /api/messages/:id/platform` `{platform}` → `platform=$platform, confidence=100` (a human reassignment is a certain signal — mirrors the reducer's own `confidence: 100` on `reassign`, `PLATFORMS` 7-value check applies). `PATCH /api/messages/:id/star` `{value}` → `is_starred=$value`. Every route validates its `ids`/`id` against `emails.id` existing (a no-op update, not an error, if an id doesn't match — matches the reducer's own silent-no-op-on-unknown-id behavior) and returns the updated row(s).
- **FR9 — `GET /api/analytics/volume`.** 14-day received-vs-handled counts, replacing `getVolumeTrend()`'s one call site in `app/page.tsx`: `select date_trunc('day', received_at) as day, count(*) from emails where received_at > now() - interval '14 days' group by 1` for `received`, and the equivalent grouped by `date_trunc('day', handled_at)` for `handled`, merged into the `{ day, received, handled }[]` shape the `VolumeTrend` chart already expects, days with zero of either filled in as `0`.

**Frontend rewiring**

- **FR10 — `board-provider.tsx` becomes the one place fixture data is replaced.** On mount, fetches `GET /api/messages` (FR6) instead of calling `getMessages()`, seeding the same `BoardState.messages` shape the reducer already uses. `archive`/`done`/`snooze`/`restore`/`reassign`/`star` actions become optimistic-update-plus-API (update local state immediately, fire the matching FR8 route, following the pattern `use-sync-state.ts` established in `008`) — `toggleVip` is unchanged (it was already purely local/ephemeral before this change; VIP has no backing column until Phase 3, so this is not a regression).
- **FR11 — `app/inbox/page.tsx`, `app/review/page.tsx`, and `components/board/board-list.tsx` need no changes.** Confirmed by reading all three: none imports from `lib/data/fixtures/*` or calls a fixture function directly — they consume `useBoard()`'s array, which FR10 makes real. This is stated as a requirement, not an assumption, so a future reviewer can verify it stayed true rather than re-deriving it.
- **FR12 — `app/page.tsx` (Overview): one fixture call replaced, one deliberately kept.** `getVolumeTrend()` → `fetch("/api/analytics/volume")` (FR9). `getAwaitingReply()` stays exactly as-is — the "waiting on them" half of the balance band needs the `commitments` table (Phase 3); this is `proposal.md`'s already-resolved decision to leave that half on fixture data, not a new gap this spec introduces.
- **FR13 — Board Sheet renders whatever the `Message` object carries.** No separate fetch — it receives its `message` prop from the same array `board-list.tsx` already holds (confirmed via `messages.find(m => m.id === openId)`), so FR6's mapping (including FR1/FR2's placeholders for thread/entities/attachments) flows through automatically. No file changes needed here beyond what FR10 already does upstream.

### Non-Functional Requirements

- **NFR1 — Field minimization, same convention as `006-draft-generation`.** `GET /api/messages` selects real columns, never `raw_payload` (untrusted, large, not part of the `Message` contract).
- **NFR2 — The 500-row bound and the 14-day analytics window are documented defaults, not silent limits.** Both are inline-commented with the reasoning (fixture parity for now; real pagination/date-range params are Phase 2+ work, not invented here).
- **NFR3 — No new n8n workflow, no change to any workflow besides Triage Pipeline.** Gmail Ingestion, Email Normaliser, Action Extraction, Draft Generation, Gmail Renewal & Recovery, LLM Gateway are all untouched — confirmed by this spec's own file list.
- **NFR4 — Auth boundary from `008` is reused, not re-implemented.** Every new route sits under the existing `/api/**` deny-by-default middleware; no route in this change re-checks the session itself.

## Acceptance Criteria

- **AC1.** A migration review confirms: `emails` has all 20 columns from FR1 with the exact types/constraints listed; `emails_category_check` (5-value) is unchanged; a new `emails_platform_check` (7-value) exists on `platform`; `tasks.email_id`'s `UNIQUE` constraint from `0003` is still present (not touched by this change).
- **AC2.** A real triage run (live Gemini call, per the project's established live-verification convention) against a test email produces an `emails` row with `platform`, `confidence`, `priority`, `priority_score`, `reasons`, `tone`, `tldr`, `entities`, `processed_at`, and `model_run` all populated, alongside the still-populated `category`/`summary` — confirmed by inspecting the row directly.
- **AC3.** A fixture-forced invalid LLM output (e.g. `platform: "not-a-real-platform"`) results in `triage_error` set and none of FR1's columns written — the whole record fails together, per FR4.
- **AC4.** An authenticated `GET /api/messages` against seeded rows returns JSON matching the `Message[]` shape from `lib/data/types.ts` — confirmed by type-checking the route's response against that interface, not just eyeballing the JSON.
- **AC5.** A message with no triage yet (`platform is null`) maps to `ai: null` in the response, and a message with `triage_error` set also maps to `ai: null` — both route to the Review queue in `app/review/page.tsx`'s existing filter, unchanged.
- **AC6.** `POST /api/messages/archive` with a real id sets `status='archived'`, `handled_at`, `handled_action='archived'` on that row and returns it; a subsequent `GET /api/messages` reflects the change.
- **AC7.** `PATCH /api/messages/:id/platform` with `{platform: "meeting"}` sets both `platform='meeting'` and `confidence=100` on that row.
- **AC8.** `GET /api/analytics/volume` against seeded rows spanning the 14-day window returns 14 entries (one per day, including zero-count days), each with non-negative `received`/`handled` integers.
- **AC9.** Manually running the dashboard against a seeded Supabase instance: the Inbox board, Review queue, and Overview's KPI strip / priority queue / volume trend all render real data with no fixture import remaining in `board-provider.tsx` or `app/page.tsx`'s `getVolumeTrend` call site (`grep -rn "getMessages\b" gmail-dashboard/components/board/board-provider.tsx` and `grep -n "getVolumeTrend" gmail-dashboard/app/page.tsx` both return nothing) — while `getAwaitingReply()` remains present in `app/page.tsx` (FR12), confirmed intentional, not overlooked.
- **AC10.** `grep -rln "getMessages\|getVolumeTrend\|getAwaitingReply" gmail-dashboard/app/inbox gmail-dashboard/app/review gmail-dashboard/components/board/board-list.tsx` returns nothing — confirming FR11's claim that these files needed no changes.

## Edge Cases

- **A message with `platform is null` and no `triage_error`** — not yet processed (queued, not failed). Maps to `ai: null` (AC5), same as a hard failure — the dashboard's `needsReview()` already treats both identically, unchanged by this spec.
- **`entities` sub-arrays the model omits entirely** — FR4 treats a missing sub-key as `[]`, not a validation failure, since an email genuinely without any dates/amounts/etc. is the common case, not an error.
- **A `reassign`/star/snooze request naming an id that doesn't exist or belongs to a different account** — the row-count-affected is 0; the route returns success with an empty result rather than a 404, matching the reducer's own tolerant behavior on an unknown id (FR8).
- **`GET /api/analytics/volume` with zero seeded rows** — returns 14 zero-filled entries, not an empty array or an error (AC8's "including zero-count days").
- **The 500-row bound hides older mail from the board.** Documented, not silently accepted — NFR2 flags it as a known, temporary limitation; real pagination is out of this phase's scope.
- **`sla_target_hours is null` for every row this phase produces** — `sla.state` is always `"ontime"`, never `"overdue"`/`"approaching"`, so the Overview's "overdue" KPI and the balance band's "you" overdue count will read `0` even for genuinely old, unanswered mail until a later phase sets a real target. This is `proposal.md`'s already-accepted open question 3, restated here so a build/verify agent doesn't mistake it for a bug.

## Dependencies

- `008-dashboard-api-foundation`'s `lib/supabase/server.ts` and auth middleware — every new route builds on these unmodified.
- `supabase/migrations/0001`–`0003` (accounts/emails base schema, `category`/`summary`/`triage_error`, `tasks`) — existing, unmodified by this change except the new `0005` migration's additive columns on `emails`.
- `n8n/workflows/llm-gateway.json` — reused unmodified (FR5 reads its model id, doesn't change the file).

## Notes

- **Why `platform` is a new column instead of widening `category`'s constraint**, despite `proposal.md`'s literal wording ("the existing `emails_category_check` constraint is widened... in practice, replaced"): re-reading `BACKEND-REQUIREMENTS.md`'s own draft SQL, that line was itself hedged ("widen... (or map in the API layer)") — it was never a settled design, just the open question the proposal inherited without fully resolving. Keeping `category` untouched is lower-risk (no breaking change to a column `004-triage`/`006-draft-generation` and their live-verification tooling already depend on being exactly 5 values) and is what the dashboard's own code actually reads (`PLATFORMS`, `getMessagesByPlatform`, `platformMeta` all key off `platform`, never `category`). This fully satisfies the proposal's intent — the dashboard gets its 7-value field — without the risk of the literal wording.
- **Why four routes from `proposal.md`'s list aren't being built** (`GET /api/messages/:id`, `GET /api/messages/counts`, `GET /api/review-queue`, `GET /api/overview`): see Overview above. Each is fully redundant with client-side derivation the current frontend already does correctly over the one array `board-provider.tsx` holds; building them would be speculative code with no caller, or would require *more* frontend rewiring than FR10 alone — the opposite of this phase's goal. If a future phase needs true server-side pagination or a public API surface independent of the dashboard's own UI, that's a better-justified reason to add them then, not now.
- **`model_run`'s value (`'gemini-3.6-flash'`) is read from `llm-gateway.json`'s live-verified model id** (see that file's own extensive note on the `gemini-2.0-flash` deprecation discovered during `004-triage`), not invented — if the Gateway's model id ever changes, this hardcoded string in the Triage Pipeline's write node needs updating too; that coupling already exists implicitly (the Gateway is the only thing that knows which model actually ran) and this spec doesn't attempt to remove it.
- The real backend's clock (`now()` in SQL, `Date.now()` in route handlers) is used throughout — deliberately diverging from `lib/data/now.ts`'s fixed fixture `NOW` (`2026-09-13T14:22:00`), which exists only to keep the fixture demo deterministic.
