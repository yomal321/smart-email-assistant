# Party Report: 003-outlook-ingestion

**Reviewed:** 2026-09-08
**Tier:** standard (classifier) — Adds Outlook ingestion as a second provider via Microsoft Graph webhooks, reusing Gmail's validated pattern; all edits are additive with bounded 6-9 file scope, unresolved architectural questions (normaliser extend or duplicate, renewal shared or separate) are deferred design decisions with fixed output interface, and schema changes follow deliberately multi-provider-ready design.
**Panel:** party-po(sonnet), party-architect(opus), party-ba(sonnet)
**Verdict:** CHANGES_REQUESTED

## Summary

13 findings: 3 BLOCK, 7 WARN, 3 NOTE upheld — 0 withdrawn

## Findings

### [BLOCK] party-architect — Scope commits to a second renewal workflow while Open Questions says the decision is unmade
**Quotes:** > Scheduled renewal workflow (same 6-hour cadence as Gmail's, reusing the pattern, not the workflow file) reading `accounts.subscription_expires_at`; re-registration on failed renewal followed by a bounded catch-up fetch, with the resulting gap window recorded in `resync_gap_start`/`resync_gap_end`
**Quotes:** > **Shared vs. separate renewal workflow** — does one n8n workflow handle renewal for both providers (branching on `accounts.provider`), or does Outlook get its own `outlook-renewal-recovery.json` mirroring `gmail-renewal-recovery.json`? Affects the file count estimate above either way.
**Problem:** In Scope the artifact settles the question — "reusing the pattern, **not the workflow file**" — which is a decision to build a second renewal-and-recovery mechanism. In Open Questions the same question is declared open. Two sections of one proposal give an implementer opposite instructions on whether a second scheduled reader of `accounts.subscription_expires_at`, a second writer of `sync_outcomes` (`renewed`/`re-registered`/`failed`), and a second writer of `resync_gap_start`/`resync_gap_end` exist. If the duplicate branch is taken, the renewal cadence, the expiry-margin arithmetic, the re-registration sequence, and the gap-window recording all exist twice against one table, and the first change to any of them diverges. The proposal gives no reason the existing renewal workflow cannot branch on `accounts.provider`, a column it relies on elsewhere for exactly this kind of discrimination.
**Fix:** Resolve the contradiction inside the proposal: either delete the Scope parenthetical and let design choose, or state in Scope why the existing renewal workflow cannot carry a provider branch. If a second workflow is genuinely intended, name every table and column both workflows will write, so the duplication is a visible cost rather than a file-count footnote.
**Status:** upheld

### [BLOCK] party-architect — `clientState` secret is given no home, while the migration is scoped as constraint-only
**Quotes:** > **Schema change required:** `accounts.provider`'s check constraint must be widened from `check (provider in ('gmail'))` to include `'outlook'`. `emails.provider` needs no change — it was already left unconstrained for exactly this. No other column changes are anticipated; Outlook's `clientState` secret and delta cursor fit the existing `n8n_credential_id`-adjacent columns and `sync_cursor` (a generic text column, not Gmail-typed) respectively.
**Quotes:** > n8n's native Microsoft Outlook OAuth2 credential is the sole owner of the token and its refresh; `accounts` holds only a reference (`n8n_credential_id`) plus sync state — never token material.
**Problem:** The delta cursor is placed in a named column (`sync_cursor`). The `clientState` secret is placed in "the existing `n8n_credential_id`-adjacent columns" — an adjacency, not a column name. No such column is identified anywhere in the artifact, and the same sentence asserts "No other column changes are anticipated", so the migration in Scope covers only the check constraint. Either an existing column is being repurposed to hold a new kind of value (which the proposal must name, because the verification step and the subscription-creation step both read it), or a column must be added and the migration is understated by a column. This also collides with the stated ownership rule one paragraph earlier: `accounts` holds "only a reference ... plus sync state", and a shared secret is neither. Two implementers reading this build two different schemas, and the notification verifier and the subscription registrar are the two components that must agree on where the value lives.
**Fix:** Name the exact storage location of `clientState` — a specific `accounts` column added by this migration, or the n8n credential/secret store — and reconcile it with the "reference plus sync state, never token material" rule for `accounts`.
**Status:** upheld

### [BLOCK] party-architect — The one contract shared by both normaliser options is left unwritten
**Quotes:** > Whether Email Normaliser itself gains an Outlook branch or a distinct "Outlook Normaliser" sub-workflow is called instead is a `/specclaw:plan`-level design decision, not resolved here (see Open Questions) — either way it must land on the identical `emails` row shape Gmail already populates, since that shape is what makes both providers a unified inbox rather than two schemas glued together downstream.
**Quotes:** > Whether Email Normaliser is extended or duplicated is undecided | Building against the wrong assumption wastes a wave of work
**Problem:** The proposal keeps open the possibility of a second writer of `emails` rows, and the sole safeguard it offers is "the identical `emails` row shape Gmail already populates" — a contract defined by pointing at an existing workflow rather than by stating it. If the duplicate branch is taken, an implementer must reverse-engineer the row shape (which fields are set, which are null-vs-empty, how provider-native labels/folders are encoded, how addresses and timestamps are normalised) from the Gmail workflow JSON, and any field the Gmail normaliser handles implicitly will be handled differently by the Outlook one. The proposal itself rates this as costing "a wave of work" if guessed wrong, which is a merge-time coupling, not a design-time nicety. This is the exact class of divergence a second writer against one table produces.
**Fix:** Either commit in this proposal to extending the existing Email Normaliser (one writer of `emails`), or, if duplication stays on the table, write the `emails` row-shape contract out field by field in the proposal so both branches are held to the same specification rather than to a reading of the Gmail export.
**Status:** upheld

### [WARN] party-architect — `sync_cursor` acquires a second grammar with no discriminator specified
**Quotes:** > Explicit fetch stage per notification using a per-account delta cursor (`sync_cursor` reused, storing a `deltaLink` rather than Gmail's `historyId`)
**Quotes:** > Delta query (`deltaLink`) expiry/invalidation semantics differ from Gmail's `historyId` in ways not yet exercised | The catch-up fallback path (time-filtered `/messages` list) may need different bounding logic than Gmail's `after:<timestamp>` fallback
**Problem:** One column now carries two incompatible value grammars — an opaque numeric `historyId` and a Graph `deltaLink`, which is a full URL — with the discriminator living implicitly in `accounts.provider`. The proposal specifies neither the stored form (bare `deltaLink` URL? extracted token? wrapped JSON?) nor what an empty/invalid `sync_cursor` means per provider, and it acknowledges the invalidation semantics differ. Every reader of `sync_cursor` must therefore branch on provider, and the artifact does not state that any existing reader is being changed to do so. Two implementers will pick two storage forms, and the fallback-bounding logic the proposal defers to design has no defined input until this is fixed.
**Fix:** State in the proposal the stored form of the Outlook cursor, the per-provider meaning of a null/stale cursor, and that reads of `sync_cursor` are provider-discriminated — or give the Outlook cursor its own column.
**Status:** upheld

### [WARN] party-architect — The webhook endpoint contract specifies only rejection, not the responses Graph requires
**Quotes:** > Microsoft Graph webhook subscription creation against the `/me/mailFolders('Inbox')/messages` (or equivalent) resource, with `clientState` verification and HTTPS-only endpoint requirement
**Quotes:** > a notification with a missing/invalid `clientState` is confirmed dropped before fetch
**Problem:** The endpoint is a new interface shared by Graph and the ingestion workflow, and the artifact specifies exactly one of its behaviours: drop on bad `clientState`. It does not specify the subscription-creation validation exchange the endpoint must answer before a subscription can exist at all, the HTTP status returned on accept versus on drop, whether acknowledgement precedes or follows the fetch stage, or how a batched notification payload containing multiple change entries is handled. Gmail's counterpart is described as "OIDC token verification (audience + issuer)", a verification-only contract, so mirroring it does not supply these. An implementer must guess, and a wrong guess on the accept path means the subscription never registers rather than failing loudly.
**Fix:** Specify the endpoint's full response contract — the validation exchange, success and rejection status codes, acknowledgement ordering relative to fetch, and multi-entry payload handling.
**Status:** upheld

### [WARN] party-architect — Every verification path requires a live subscription and wall-clock waiting; no stub seam is named
**Quotes:** > *Same-day:* a manually sent test email to the target Outlook account appears normalized in `emails` within seconds via a live Graph webhook delivery (not polling), and a notification with a missing/invalid `clientState` is confirmed dropped before fetch.
**Quotes:** > *Multi-day:* at least one renewal cycle for the Outlook subscription is observed to fire and succeed.
**Quotes:** > Target account: TBD — needs a personal Outlook.com or Microsoft 365 mailbox nominated before `/specclaw:plan`
**Problem:** All three verification paths bind to live Microsoft infrastructure: a live webhook delivery, an observed renewal tick over multi-day wall-clock, and a mailbox that does not yet exist. The design names no seam at which a notification payload, a `/messages/delta` response, or an expiry timestamp can be injected, so the `clientState` rejection branch, the dedup replay, the delta-token-expired fallback, and the re-registration path have no offline test. The fallback path in particular is described as differing from Gmail's and "not yet exercised", meaning the least-understood branch is the one hardest to trigger on demand — it fires only when Graph decides to invalidate a token.
**Fix:** Name the stub seam in the proposal: a fixture notification payload replayed against the endpoint, a recorded delta response, and a forced-past `subscription_expires_at` to trigger renewal and re-registration without waiting for the real window.
**Status:** upheld

### [NOTE] party-architect — Rebuttal of party-ba's "two separate schemas sitting in one table" reading
**Quotes:** > Cross-provider label/folder reconciliation (e.g. treating Gmail's "Inbox" label and Outlook's Inbox folder as one concept) — each provider's native labels/folders are stored as-is, same lossless-not-unified approach `002-ingestion` took for Gmail labels
**Quotes:** > either way it must land on the identical `emails` row shape Gmail already populates, since that shape is what makes both providers a unified inbox rather than two schemas glued together downstream
**Problem:** party-ba reads the out-of-scope label/folder item as meaning the change delivers "two separate schemas sitting in one table". Structurally that reading overstates the divergence: the artifact mandates one row shape in one table with one dedup constraint, and confines the non-reconciliation to the values inside the provider-native label/folder field. One schema with a provider-varying value domain in one field is not two schemas. I take no position on whether the resulting benefit is worth claiming — that is party-ba's and party-po's arrow, and their finding may well stand on the benefit argument alone. I contest only the schema-level characterisation, and I note it does not weaken my own BLOCK above: the proposal *intends* one row shape but never writes it down, which is a specification gap, not evidence of two schemas.
**Fix:** party-ba may wish to rest the finding on the "unified inbox" benefit claim rather than on a two-schemas structural premise the artifact's own text contradicts.
**Status:** upheld

### [WARN] party-ba — "Unified inbox" is claimed as the benefit but the proposal's own scope declares it will not unify anything
**Quotes:** > Nothing downstream (triage, action extraction, drafting) can treat "the inbox" as unified while one of the two providers it's supposed to unify isn't wired in yet.
> Cross-provider label/folder reconciliation (e.g. treating Gmail's "Inbox" label and Outlook's Inbox folder as one concept) — each provider's native labels/folders are stored as-is, same lossless-not-unified approach `002-ingestion` took for Gmail labels
**Problem:** The Problem section's justification for building this now is that downstream code "can treat 'the inbox' as unified" once both providers are wired in. The Out of Scope section then states the opposite outcome will ship: labels/folders are kept "lossless-not-unified," i.e. two separate schemas sitting in one table, not a unified concept. Even if this ships and works perfectly, nothing downstream gains a unified inbox — it gains two parallel non-reconciled data streams, and no AI/triage exists yet to consume either (also out of scope). The real, evidenced problem is narrower and truer: "the Phase 1 checklist requires both providers on push-based sync" — that premise is fine on its own, but the proposal inflates it into an "enables unification" claim its own scope disclaims.
**Fix:** Restate the problem as satisfying the explicit Phase-1 two-provider checklist item, and drop or qualify the "unified inbox" framing so it doesn't imply a benefit this change does not deliver.
**Status:** upheld

### [WARN] party-ba — Token-material exposure "criterion" is deferred to another document and is not restated or falsifiable here
**Quotes:** > *No new criterion needed for token-material exposure* — AC5's schema review from `002-ingestion` already covers `accounts` for both providers once the constraint migration lands; re-running it after this change ships is the confirmation, not a new acceptance criterion.
**Problem:** This is presented as a Done-when item but contains no observable pass/fail condition in this document — it asserts that an external artifact ("AC5" from `002-ingestion`) already covers the new case, without restating what AC5 checks or what would make it fail for the Outlook path specifically (e.g., a `clientState` secret or `deltaLink` accidentally landing somewhere token material shouldn't). As written, there is nothing in this proposal a reviewer could check against reality to falsify this bullet.
**Fix:** Either restate AC5's actual check inline (so it's verifiable from this document alone) or explicitly scope this proposal's Done-when list to only the criteria that are self-contained, and note the external dependency separately from the acceptance list.
**Status:** upheld

### [NOTE] party-ba — Graph subscription max-lifetime figure is asserted without a source and underpins the renewal-margin risk claim
**Quotes:** > Graph mail subscriptions max out around 4230 minutes (~2.9 days), well inside a 6h cadence, same margin logic as Gmail's ~7-day window
**Problem:** The "~12x margin" risk mitigation later in the document is arithmetic built on this 4230-minute figure, but no Microsoft documentation, changelog, or prior test is cited for it. If the real maximum differs (Graph's mail-resource subscription limits have changed over API versions), the stated margin and the "well inside a 6h cadence" comfort claim would be wrong, and this number is the only evidence offered for treating the shorter Outlook renewal window as low-risk rather than as a reason to shorten the cadence.
**Fix:** Cite the Graph API documentation page/version the 4230-minute figure comes from, so the margin claim can be checked rather than taken on faith.
**Status:** upheld

### [WARN] party-po — Do-nothing cost is asserted from a spec criterion, never quantified against actual usage
**Quotes:** > But the umbrella proposal's (`001-smart-email-assistant`) Phase 1 success criterion is explicit: **both inboxes syncing reliably on push, not polling.** Gmail alone is half of Phase 1, not all of it.
**Problem:** The entire justification for this change's cost (new OAuth flow, webhook subscription, clientState verification, delta-cursor fetch, 6h renewal workflow, catch-up fallback, a schema migration) is "an internal phase-completion criterion says so." Nowhere does the proposal state how many emails, how often, or with what user-facing consequence flow through the target Outlook account if this ships in no form — the "cost of doing nothing" is entirely definitional (a checklist item stays unchecked), not usage-quantified. A criterion being explicit doesn't make the value it protects nonzero in practice; the proposal never says.
**Fix:** State the expected email volume/cadence on the target mailbox, or explicitly note that value here is unified-inbox-architecture value rather than volume value, so the cost/value trade is visible rather than assumed.
**Status:** upheld

### [WARN] party-po — Recurring execution cost of the renewal/notification machinery is never sized
**Quotes:** > Scheduled renewal workflow (same 6-hour cadence as Gmail's, reusing the pattern, not the workflow file) reading `accounts.subscription_expires_at`; re-registration on failed renewal followed by a bounded catch-up fetch, with the resulting gap window recorded in `resync_gap_start`/`resync_gap_end`
**Problem:** This workflow runs forever, on a cadence tighter-margin than Gmail's (per the proposal's own risk table: "~12x margin" inside a 3-day window vs. Gmail's larger slack), plus a per-notification fetch workflow for every inbound message. The proposal gives no number for how many n8n executions/month this adds, what that costs against any n8n plan/execution limits, or what operator attention is needed if the tighter margin causes more frequent missed-cycle recovery than Gmail's pattern ever needed. A recurring cost that runs indefinitely and is stated to have *less* margin than the precedent it's copied from should carry a number, not just an analogy. This is sharpened, not resolved, by party-architect's finding that a second, duplicate renewal workflow may be built (Scope says "not the workflow file") — if that branch is taken, the unstated recurring cost is doubled, not merely unstated.
**Fix:** State expected renewal-workflow executions/month and per-notification-fetch executions/month, and confirm these stay within whatever infra budget/plan is in force.
**Status:** upheld

### [NOTE] party-po — The migration has independent value and a cut line the proposal doesn't name
**Quotes:** > One concrete schema gap this proposal surfaces from reading `0001_ingestion_schema.sql` directly: `accounts.provider` carries `check (provider in ('gmail'))` — a hard constraint, not just a convention. Adding Outlook requires a small migration to widen that check, which `emails.provider` (unconstrained) does not need. This is smaller than a rewrite, but it is a migration, and should be scoped as one rather than assumed away.
**Problem:** The proposal correctly isolates this as its own migration but never asks whether it should ship on its own, ahead of the full webhook/renewal build. Widening the constraint is valuable and low-risk in isolation (unblocks any future `accounts` insert for `'outlook'`, testable independent of Graph subscriptions), and shipping it first would let the schema half of this change land and be verified days before the OAuth/webhook mechanics are ready — rather than the two being bundled into one ~6–9 file change that ships or doesn't ship together. This cut line is now more valuable given party-architect's finding that the migration itself is understated (missing a home for `clientState`) — surfacing the migration as its own slice, sized correctly, before the webhook build starts, would catch that gap earlier and cheaper than finding it mid-build.
**Fix:** Name the migration as an independently-shippable first slice in the scope section, not just an item inside the combined change.
**Status:** upheld
