### [WARN] party-po — Do-nothing cost is asserted from a spec criterion, never quantified against actual usage
**Quotes:** > But the umbrella proposal's (`001-smart-email-assistant`) Phase 1 success criterion is explicit: **both inboxes syncing reliably on push, not polling.** Gmail alone is half of Phase 1, not all of it.
**Problem:** The entire justification for this change's cost (new OAuth flow, webhook subscription, clientState verification, delta-cursor fetch, 6h renewal workflow, catch-up fallback, a schema migration) is "an internal phase-completion criterion says so." Nowhere does the proposal state how many emails, how often, or with what user-facing consequence flow through the target Outlook account if this ships in no form — the "cost of doing nothing" is entirely definitional (a checklist item stays unchecked), not usage-quantified. A criterion being explicit doesn't make the value it protects nonzero in practice; the proposal never says.
**Fix:** State the expected email volume/cadence on the target mailbox, or explicitly note that value here is unified-inbox-architecture value rather than volume value, so the cost/value trade is visible rather than assumed.
**Status:** upheld

### [WARN] party-po — Recurring execution cost of the renewal/notification machinery is never sized
**Quotes:** > Scheduled renewal workflow (same 6-hour cadence as Gmail's, reusing the pattern, not the workflow file) reading `accounts.subscription_expires_at`; re-registration on failed renewal followed by a bounded catch-up fetch, with the resulting gap window recorded in `resync_gap_start`/`resync_gap_end`
**Problem:** This workflow runs forever, on a cadence tighter-margin than Gmail's (per the proposal's own risk table: "~12x margin" inside a 3-day window vs. Gmail's larger slack), plus a per-notification fetch workflow for every inbound message. The proposal gives no number for how many n8n executions/month this adds, what that costs against any n8n plan/execution limits, or what operator attention is needed if the tighter margin causes more frequent missed-cycle recovery than Gmail's pattern ever needed. A recurring cost that runs indefinitely and is stated to have *less* margin than the precedent it's copied from should carry a number, not just an analogy.
**Fix:** State expected renewal-workflow executions/month and per-notification-fetch executions/month, and confirm these stay within whatever infra budget/plan is in force.
**Status:** upheld

### [NOTE] party-po — The migration has independent value and a cut line the proposal doesn't name
**Quotes:** > One concrete schema gap this proposal surfaces from reading `0001_ingestion_schema.sql` directly: `accounts.provider` carries `check (provider in ('gmail'))` — a hard constraint, not just a convention. Adding Outlook requires a small migration to widen that check, which `emails.provider` (unconstrained) does not need. This is smaller than a rewrite, but it is a migration, and should be scoped as one rather than assumed away.
**Problem:** The proposal correctly isolates this as its own migration but never asks whether it should ship on its own, ahead of the full webhook/renewal build. Widening the constraint is valuable and low-risk in isolation (unblocks any future `accounts` insert for `'outlook'`, testable independent of Graph subscriptions), and shipping it first would let the schema half of this change land and be verified days before the OAuth/webhook mechanics are ready — rather than the two being bundled into one ~6–9 file change that ships or doesn't ship together.
**Fix:** Name the migration as an independently-shippable first slice in the scope section, not just an item inside the combined change.
**Status:** upheld
